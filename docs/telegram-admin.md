# Заявки на токены и Telegram-админка

Клиент запрашивает дополнительные токены в `/account`. Администратор проверяет оплату вручную и одобряет заявку в личном чате с ботом или Mini App `/admin`. Начисляется **добавочное количество**, а не новый абсолютный баланс. Автоматической проверки блокчейна/платёжной интеграции пока нет.

Временный тариф владельца: 0,1 USDT за 10 000 токенов; 50 000 — 0,5; 100 000 — 1; 500 000 — 5 USDT. Произвольное количество — пропорционально, округление вверх до 0,000001 USDT. Настройка `token_payment_settings.price_per_10000_micros = 100000` хранится на сервере; обновлять SQL, без пересборки фронтенда. Публичные адреса USDT для TON, Tron, Solana, Ethereum и BNB Smart Chain хранятся в `token_payment_networks` (миграция 0010). У заявки сохраняются сеть, адрес и сумма на момент создания. Клиентская цена сверяется с текущей серверной; изменение тарифа требует обновления формы, но не меняет старые заявки.

Кабинет сначала создаёт заявку, затем показывает сохранённые реквизиты и сумму с кнопками копирования. Активная заявка видна отдельно от истории и восстанавливается после перезагрузки. После оплаты клиент передаёт хеш транзакции (до трёх изменений); он повторно отправляется владельцу. Хеш — ссылка для ручной проверки, не доказательство оплаты: сверять сеть, USDT, получателя, сумму и отсутствие повторного использования транзакции перед одобрением.

## Возможности

- Пакеты 10 000, 50 000, 100 000, 500 000; произвольное целое 10 000–1 000 000 000.
- Комментарий, история, статусы; обновление истории каждые 15 секунд при открытой вкладке.
- В боте: `/start`, `/clients`, `/clients email или имя`, `/requests`, `/stats`. Кнопка «Клиенты» показывает всех зарегистрированных, даже без заявок. Нажатие на клиента открывает баланс, покупки, расход, проекты, даты регистрации/входа и историю. Общий список и история имеют пагинацию; поиск в чате показывает первые 20 совпадений (для остальных уточнить запрос или использовать Mini App). Сообщения отправляются исключительно в приватный чат `7145160476`; сообщения других пользователей и групп игнорируются.
- Mini App: вкладка «Клиенты» содержит каталог с поиском по имени/email/ID и страницами по 20. Источник — `auth.users`, а не заявки. RPC `token_admin_clients` (0011) закрыт для браузерных ролей; доступ только через серверную авторизацию владельца.
- Mini App: поиск по email/ID заявки, фильтры, пагинация, история клиента, покупки/бонусы/расход/баланс, число зарегистрированных пользователей и проектов, комментарий решения, повтор доставки уведомлений.
- Покупка (`purchase`) — ручная проверка оплаты; бонус (`grant`) — бесплатное начисление из Mini App. Стартовые 50 000 учитываются только в балансе, не в покупках. Исторические покупки вне новой системы не восстанавливаются из остатка баланса.

## Сервер и безопасность

- `token-request` проверяет Supabase access token через `auth.getUser`. Клиентский `user_id` не принимается.
- `telegram-admin` проверяет HMAC подписанного `Telegram.WebApp.initData`, срок до часа и единственный разрешённый ID. После истечения часа закрыть/открыть Mini App. Авторизация не сохраняется в localStorage.
- Webhook `/telegram-admin/webhook` проверяет `X-Telegram-Bot-Api-Secret-Token`, ID отправителя, приватный тип и ID чата. Административные данные не выдаются обычной странице `/admin` без Telegram.
- Таблица `token_requests`: RLS только на чтение собственных заявок; запись доступна только server role. SQL RPC отозваны у public/anon/authenticated. Секретный ключ Supabase и токен бота никогда не передаются браузеру.
- Одна pending-заявка и лимит 5 за 24 часа проверяются под блокировкой. Повтор запроса с прежним UUID возвращает прежнюю запись. `decide_token_request` блокирует строку заявки; изменение статуса и баланса — одна транзакция. Повторный/конкурирующий approve/reject не меняет уже принятое решение.
- Уведомления имеют lease на 2 минуты. pg_cron каждую минуту вызывает защищённый `/retry` через pg_net, пока имеются неотправленные заявки; до 10 за проход. Возможный дубль Telegram при потере сетевого ответа не приводит к повторному начислению. Отклонённые/одобренные заявки больше не доставляются как новые.
- Статистика накопительная, заявки — по 20 на страницу. Для удаления аккаунтов используется существующий cascade; при будущем финансовом/юридическом учёте потребуется отдельный неизменяемый журнал операций и политика хранения.

## Развёртывание

Фронтенд остаётся статическим GitHub Pages, backend — уже используемый Supabase. VPS для этого варианта не нужен.

1. `supabase db push --linked` применяет миграции по 0011 включительно. Не редактировать применённые миграции.
2. Создать игнорируемый `.env.telegram` (не `.env`, не публичные переменные):

   ```dotenv
   TELEGRAM_BOT_TOKEN=<bot token>
   TELEGRAM_WEBHOOK_SECRET=<random 64-char hex>
   TELEGRAM_ADMIN_APP_URL=https://maaloznal.github.io/cardcraft_v2/admin/
   TOKEN_ALLOWED_ORIGINS=https://maaloznal.github.io,http://localhost:3000
   ```

3. `supabase secrets set --env-file .env.telegram`.
4. `supabase functions deploy token-request telegram-admin --no-verify-jwt --use-api`. Gateway JWT отключён, потому что Mini App/webhook используют Telegram; пользовательский JWT `token-request` обязательно проверяет сам. Никогда не удалять внутренние проверки.
5. `node scripts/configure-telegram.mjs --vault-sql`, затем `supabase db query --linked --file local-token-vault.sql`. Удалить этот локальный секретный SQL после применения. Секреты очереди хранятся в Vault; cron SQL не содержит секретов.
6. Опубликовать frontend со страницей `/admin`. Владелец должен первым открыть бота и нажать Start.
7. `node scripts/configure-telegram.mjs` устанавливает webhook, команды и кнопку меню только для владельца, отправляет ему сообщение. `--inspect` проверяет состояние без вывода токена. Не использовать `--debug` при передаче секретов.

В BotFather можно дополнительно включить Main Mini App и указать тот же HTTPS URL. Inline-кнопка и персональное меню уже запускают Mini App без этой настройки. Любой другой Telegram-пользователь всё равно получит отказ сервера.

## Проверки

- `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`.
- `npx playwright test tests/e2e/token-admin.spec.ts tests/e2e/nav-docs-changes.spec.ts --project=chromium`.
- `supabase db query --linked --file tests/database/token-requests.sql` — rollback-тест фиктивных пользователей, начисления, идемпотентности, отклонения, RLS и закрытых RPC. Реальные балансы не изменяет.
- `supabase db query --linked --file tests/database/token-payments.sql` — rollback-тест суммы, адреса, устаревшей цены и неизменяемости сохранённой заявки.
- `supabase db query --linked --file tests/database/admin-clients.sql` — rollback-тест каталога всех клиентов, включая аккаунты без заявок, поиска, пагинации и закрытого доступа к RPC.
- `node scripts/test-token-admin-live.mjs` — явно запускаемый live smoke-test; требует `.env.integration` с `SUPABASE_SECRET`. Создаёт два временных пользователя, проверяет серверную авторизацию, RLS, заявку и три конкурентных одобрения, затем удаляет тестовые данные и сообщение. Не писать секреты/ответы авторизации в вывод.
- `tests/unit/telegram-auth.test.ts` использует независимую Node HMAC-подпись; чужой ID, подмена, повторы полей, просрочка и другой бот должны быть отклонены.

## Перенос на VPS

Нужен HTTPS-домен. Можно разместить тот же `out/` под `/cardcraft_v2/`, сохранив basePath, а backend оставить в Supabase. Для домена в корне отдельно изменить production basePath и OAuth redirect allowlist. Обновить `TELEGRAM_ADMIN_APP_URL`, `TOKEN_ALLOWED_ORIGINS`, BotFather URL при наличии, затем повторить configure-telegram. В reverse proxy разрешить embedding `/admin` только для `https://web.telegram.org https://*.telegram.org` через CSP frame-ancestors и официальный SDK `https://telegram.org` в script-src; не выставлять X-Frame-Options DENY для Mini App. У остальных страниц можно оставить frame-ancestors 'none'. Заголовки next.config не переносятся в статические файлы автоматически.
