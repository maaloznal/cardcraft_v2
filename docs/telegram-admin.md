# Оплата Crypto Bot и уведомления администратора

Новые пополнения в `/account` оплачиваются счётом Crypto Pay в USDT. Сервер создаёт счёт, сохраняет его ID, сумму, срок и ссылку. Секрет `CRYPTO_PAY_API_TOKEN` хранится только в Supabase Secrets; локальная копия `.env.crypto` исключена из Git.

Минимальный чек — **1 USDT**. Расчёт: `max(1 USDT, ceil(tokens × price_per_10000_micros / 10000))` в микродолях USDT. Текущая ставка 0,1 USDT за 10 000 даёт 10 000 / 50 000 / 100 000 за 1 USDT и 500 000 за 5 USDT. Существующие ручные заявки сохраняют исходные реквизиты и цену.

## Подтверждение и доставка

- `crypto-pay-webhook` проверяет HMAC-SHA256 исходного тела с ключом SHA256 токена Crypto Pay. Подпись проверяется до разбора JSON.
- Проверяются сохранённый invoice ID, payload с UUID заявки, статус `paid`, валюта USDT и точная сумма. Идентификатор webhook не используется для дедупликации: Crypto Pay не гарантирует его уникальность.
- `settle_crypto_invoice` блокирует строку заявки и атомарно начисляет токены с сохранением платежа. Повторы не меняют баланс. Поздняя подтверждённая оплата закрытого счёта также начисляется ровно один раз.
- Ручное одобрение/отклонение автоматического счёта заблокировано в базе и скрыто в админке. Старые ручные заявки обслуживаются прежним способом.
- После начисления администратор `7145160476` получает сообщение с клиентом, суммой, комиссией Crypto Pay, количеством токенов, номером счёта и датой оплаты. Это поступление в приложение Crypto Pay, а не вывод на внешний кошелёк.
- Существующий cron каждую минуту перепроверяет неоплаченные счета через `getInvoices` и повторяет недоставленные уведомления. Кабинет также проверяет активный счёт каждые 15 секунд. Просроченные счета закрываются, освобождая место для нового.
- Уведомление имеет lease 2 минуты. При потере сетевого ответа Telegram возможен повтор сообщения, но не повтор начисления. Сбой Crypto Pay не мешает доставке уже сохранённых уведомлений.
- Счёт действует час. При отмене сервер сначала проверяет оплату, затем удаляет неоплаченный счёт у провайдера. Создание конкурирующих счетов сохраняет и показывает только первый; лишний удаляется или истекает без показа клиенту.

## Развёртывание

1. `supabase db push --linked` (миграции по 0013).
2. Сохранить `.env.crypto` с `CRYPTO_PAY_API_TOKEN=...`, затем `supabase secrets set --env-file .env.crypto`. Для отдельного тестового окружения добавить `CRYPTO_PAY_TESTNET=true`; не смешивать mainnet/testnet счета в одной базе.
3. `supabase functions deploy token-request telegram-admin crypto-pay-webhook --no-verify-jwt --use-api`. JWT шлюза отключён для webhook; пользовательские запросы проверяют Supabase JWT внутри функции, Telegram — собственную подпись и владельца.
4. Crypto Bot → Crypto Pay → My Apps → Cardcraft → Webhooks: включить `https://rbvokjedmyndntojvekn.supabase.co/functions/v1/crypto-pay-webhook`. Самоподписной сертификат не нужен.
5. Для первоначальной настройки Telegram: `.env.telegram`, `supabase secrets set --env-file .env.telegram`, `node scripts/configure-telegram.mjs --vault-sql`, применить полученный локальный SQL в Vault и удалить его. `node scripts/configure-telegram.mjs --inspect` проверяет бота без изменения настроек.
6. Опубликовать фронтенд. Проверить реальную оплату минимального счёта владельцем: поступление в Crypto Pay, одно начисление, уведомление в админ-боте.

## Проверки

- `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`.
- `npx playwright test tests/e2e/token-admin.spec.ts tests/e2e/selection-docs.spec.ts --project=chromium`.
- `supabase db query --linked --file tests/database/crypto-pay.sql` — rollback-проверка минимума, привязки счёта, запрета ручного решения, неверной суммы/валюты, поздней оплаты, повторов, lease и закрытых прав RPC.
- Прежние SQL-тесты ручных заявок остаются актуальны. `scripts/test-token-admin-live.mjs` относится к прежнему ручному сценарию и не используется для Crypto Pay.
