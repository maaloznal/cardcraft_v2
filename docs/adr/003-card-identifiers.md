# ADR-003: Card Identifiers — Stable `data-card-id` Replaces Positional `data-index`

**Date**: 2025-09-11
**Status**: Accepted

## Context

The original `index.html` identified card elements positionally with `data-index="${i}"` — every render loop embedded the array index into the DOM. Handlers read the index back with `Number(el.dataset.index)` and used it directly to look up the card in state. This worked as long as the DOM and state array were rebuilt in lockstep on every mutation.

P1-1 (audit) found the breaking case: any operation that mutated state without a full DOM rebuild left stale indices on the surviving elements. The simplest reproduction was delete-card-2 from a 3-card deck:

1. Before: card-wrappers have `data-index` 0, 1, 2; state array has 3 cards.
2. `DELETE_CARD` splices state index 1 → state array is now `[card0, card2]` (length 2).
3. The new O(1) `removeCard` path removes the middle DOM node but does **not** re-emit `data-index` on the surviving nodes.
4. Card 2's wrapper still says `data-index="2"`, but it now lives at state index 1. The next click on its "delete" button calls `stateManager.getCard(2)` → `null` → silent no-op (or worse, deletes a different card if the array has since grown).

The same staleness affected `dblclick` (word-style popup opened on the wrong card) and the per-card color palette (edits landed on the wrong card). With three O(1) mutation paths (`removeCard`, `insertCard`, `moveCard`) all skipping full rebuilds, positional indices were no longer safe.

## Decision

**Identify card elements by stable `data-card-id` derived from `card.id` (a UUID generated by `generateId()`). The orchestrator resolves the array index from `cardId` via `Array.findIndex` at action time.**

Implementation:

- Each card's `.card-wrapper` and every field-bearing element (`[data-field]`, list items, action buttons) carry `data-card-id="${sanitizeCardId(card.id)}"` — see `PreviewRenderer.buildCardWrapper` (`src/preview/PreviewRenderer.ts` lines 234, 243, 266, 273–280) and `createFieldElement` (line 310).
- The card node itself is reachable in O(1) via `document.getElementById('card-node-' + safeCardId)` — see `getCardNode` (lines 205–208).
- `sanitizeCardId` (`src/core/utils.ts` lines 81–85) validates against `^[a-zA-Z0-9_-]{1,64}$` and falls back to a fresh UUID on invalid input — defense against XSS via crafted IDs in localStorage.
- On delete-preview / dblclick, the orchestrator strips the `card-node-` prefix and resolves the index: `const idx = stateManager.getCards().findIndex(c => c.id === cardId)` (`src/orchestrator/callbacks.ts` lines 37–39, 44–45). Only after the index is resolved does the operation dispatch.
- The EditorRenderer still uses `data-index` on its inner inputs/textareas because the editor is rebuilt after every structural change (`reindexBlocks` runs on add/delete/duplicate/move — `src/editor/EditorRenderer.ts` lines 121–148). The editor never has stale indices because its DOM is reindexed synchronously with state mutations. The preview, however, uses `data-card-id` exclusively because its O(1) paths skip rebuilds.

## Consequences

- **Positive**:
  - Delete/duplicate/move no longer require a full preview rebuild — `removeCard(cardId)`, `insertCard(card, index)`, and the DOM swap in `card-ops.ts` `moveCard` (lines 122–144) all stay O(1).
  - Word-style popup and per-card palette always target the correct card even after reorders — the bug class that motivated P1-1 is closed.
  - `card.id` is a UUID generated once at card creation (`createEmptyCard` in `StateManager.ts` line 438) and never mutated, so the binding is stable for the card's entire lifetime.
  - DOM lookup is O(1) (`getElementById`) — the only O(n) cost is `findIndex` at action time, and n is small.

- **Negative**:
  - Every action that needs an index pays an O(n) `findIndex` — fine for typical decks (<100 cards), but the lookup runs on every delete/dblclick/palette-open.
  - Two identifier systems coexist (`data-index` in the editor, `data-card-id` in the preview). New contributors must learn which surface uses which — the editor reindexes on every structural change, the preview doesn't.
  - `sanitizeCardId` is called in multiple render paths (build wrapper, create field element, update list) — a future cleanup could centralize this in one place.

- **Neutral**:
  - The `Action` union still uses `idx: number` payloads (`src/core/types.ts` lines 136–165) — the orchestrator converts `cardId → idx` before dispatching. A future refactor could switch the Action payload itself to `cardId: string` (noted in `types.ts` lines 127–131 as out-of-scope for P1), but that would touch every reducer case.

## Verification

- `src/preview/PreviewRenderer.ts` lines 205–208 (`getCardNode` O(1) by cardId), 234 (`sanitizeCardId(card.id)`), 266 (`wrapper.dataset.cardId`), 310 (field elements get `data-card-id`).
- `src/orchestrator/callbacks.ts` lines 35–55 (delete-preview + dblclick resolve idx from cardId via `findIndex`).
- `src/core/utils.ts` lines 81–85 (`sanitizeCardId` regex + UUID fallback).
- `src/state/StateManager.ts` line 438 (`createEmptyCard` calls `generateId()`).
- `tests/e2e/cards.spec.ts`: delete/reorder then operate on the surviving card — exercises the index-from-cardId resolution.
